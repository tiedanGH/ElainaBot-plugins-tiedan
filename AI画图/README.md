# AI 画图

任何人都能用的文生图插件。群聊、私聊里发 `画图 <描述>` 就出图（不支持 QQ 频道）。

接口、密钥、模型目录全部由 `modules/ai_llm` 中央模块管理，**本插件不保存任何凭据**，
只在自己的配置里记 `provider_id` / `model` 这种选择。

---

## 依赖

| 模块 | 必需 | 说明 |
|---|---|---|
| `modules/ai_llm` | ✅ | 至少配好一个支持生图的接口与模型；对外画图工具不依赖它的工具共享（1.3 已去掉） |
| `modules/image_hosting` | 推荐 | 出图后上传图床拿直链，才能发 Markdown 图片消息；**对外公开画图能力时必需** |

缺 AI LLM 时面板整体灰化并提示去插件市场下载；缺图床时自动退回富媒体图片消息。

---

## 指令

| 指令 | 权限 | 说明 |
|---|---|---|
| `画图 <描述>` | 所有人 | 生成并发送一张图 |
| `绘图` / `AI画图` | 所有人 | 别名，用法相同 |
| `画图` | 所有人 | 查看用法、当前尺寸、可用线路数 |

支持可选 `/` 前缀，描述可跨行；最大字数在面板「限流」页可调（默认 1000）。

## 为什么要走图床

QQ 的富媒体消息（`msg_type=7`）**不解析 `<@openid>`** —— 直接 `reply_image` 的话，
开头的 @ 只会以原文形式显示。所以默认改发 Markdown（`msg_type=2`）：

```
<@用户openid> 可选说明文字
![AI画图 #1024px #1024px](https://图床直链)
```

图片先经 Image Hosting 上传；接口只返回 URL 时会先下载再上传，保证域名是自己配的图床。
`#Wpx #Hpx` 由不依赖 Pillow 的头部解析器读出（PNG / JPEG / GIF / WebP）。

> ⚠️ **Markdown 图片的域名必须已在 QQ 开放平台报备**，否则图片不显示。
> 开着「校验图片资源」时未报备会判失败并退回富媒体，不会静默发出一条空图。

三级降级：图床上传失败 → 平台拒绝 Markdown → 退回富媒体图片消息。
私聊不带 @（没有提及语义），群聊按「群内 @发起人」开关决定。

### 发送成功的判据

`reply()` / `reply_image()` 在平台失败时**也会返回响应体**（错误 JSON），
所以 `bool(response)` 判不出成败，必须看 `response['id']` 有没有消息 ID。
判错的话 Markdown 失败永远不会触发降级。

### 生成成功却没送达 → 换线路重来

常见于接口只返回一个 URL、而那个 URL 本地下不下来、平台也拉不动（链接过期、
指向内网、被防盗链挡住）。这时图是「生成成功」的，用户却什么都没收到。

所以投递失败会被判定为**这条线路的问题**，自动排除它、用下一条线路重新生成，
次数由面板「投递失败换线路重试次数」控制（默认 2，最多 5，同时不超过可用线路数）。

只有一种失败不重试：**图床上传成功、Markdown 却被平台拒收**。那是图床域名没报备，
换线路拿到的还是同一个域名，重试纯属白烧额度。

成功送达时历史里会记下先前失败的线路；全部试完仍失败则逐条记录原因。
单图模式下用户始终只会收到一张图或一条失败提示，不会重复。

## 多图模式：几条线路同时出图

依次故障转移的问题是**慢**：GPT 系线路正常 60 秒、偶尔 180~240 秒，挂掉以后才轮到下一条，
加起来很容易超过 QQ 被动回复的 5 分钟有效期 —— 到那时图画好了也发不出去。

**开启方式**：先在「生图线路」页给至少两条线路勾上**多图**并保存，再打开概览页的**多图模式**开关
（默认关；勾了多图的启用线路不足两条时开关打不开）。开启后这些线路**同时**各画一张：

```
0s     开始审核 → 改写提示词 → 勾了多图的线路同时开画
180s   「多图汇总等待」到点（或者全部画完，以先到者为准）
       └→ 已画好的拼成一条 Markdown 发出去；没画完的接着画，不另发提示
 …     剩下的谁画好谁补发
290s   硬截止：还没画完的放弃并留档
```

时间都**从开始审核算起**：QQ 群聊被动回复在用户发消息 5 分钟后失效，框架也会在 300 秒时
掐断处理器，留出最后十来秒把最后一批图发出去。**单图模式同样受这条 290 秒线约束**，
到点就不再换线路重试。汇总等待可调（10~280 秒，默认 180）。

| 情况 | 处理 |
|---|---|
| 汇总前全部画完 | 不等汇总时间，立刻一条 Markdown 带齐所有图（图之间空一行） |
| 汇总时画好一部分 | 先发画好的；之后每画好一张补发一张 |
| 汇总时一张都没好 | 什么都不发，接着等，画好就发 |
| 某条线路报错 | 只记它的失败，其他线路照常，**不再按顺序换线路**（那正是要避免的慢） |
| 多图线路全部失败 | 按顺序试一遍**没勾多图**的线路兜底（剩余不足 20 秒就不试了） |
| 全部失败且没有备用 | 回失败提示 |
| 到 290 秒还没画完 | 取消请求，记为失败 |

**线路超时只给重试模式用**：多图里勾了多图的线路不按各自的超时提前掐断，只受 290 秒总时限约束
（走中央模块的生图端点仍有中央自己的 180 秒上限）；兜底的备用线路是顺序重试，照常用各自的超时。

开关开着、但可用的多图线路掉到不足两条（取消勾选、接口停用、模型下架）时，自动退回原来的顺序重试，
概览页开关下方会标黄提示。

每张图的图片说明（`caption_template`）各自渲染在自己那张图上方。

### 被动回复次数

QQ 每条用户消息群聊最多被动回复 **5 次**、私聊 **4 次**，「正在作画」提示也算一次。
所以补发得算着用：每次补发前看「发完还剩不剩一次给没画完的」，不剩就先攒着，
等剩下的都画完（或到 290 秒）拼成最后一条一起发。五六条线路同时画也不会撞上次数上限，
只是最后几张合并成一条到达。

没有图床（或关了 Markdown）时退回富媒体：一张图一条消息，次数用完的图记为未送达。
Markdown 被平台拒收时，开着「失败退回富媒体」就整批改发富媒体。

### 成本与额度

| 项 | 规则 |
|---|---|
| 并发 | 一次多图请求只占**一个**并发名额（按张占的话，名额一满又变回排队挨个画） |
| 每日额度 | 按出图**张数**算；今天剩余额度不够就少开几路，只剩一张时退回单图 |
| 历史记录 | 每张图一条记录，同一次请求共用 `batch_id`；运行日志里标「多图 xxxx」 |
| 统计 | 「累计请求 / 今日请求」按批次折算成一次，「成功出图」按张数 |
| 图床 | 每张图各传一次；文件名带随机后缀，同一毫秒传完也不会互相覆盖 |

勾了多图的线路照样可以选出图端点。不足两条可用的多图线路时整套逻辑退回单图（顺序重试）。

## Gemini 等多模态模型：走对话端点

`gemini-3.1-flash-image`（Nano Banana 2）这类模型**不是纯生图模型，而是多模态 LLM**，
所以多数中转不把它挂在 `/v1/images/generations` 上。直接当生图模型调会收到：

```
HTTP 400: Model gemini-3.1-flash-image is not supported on /v1/images/generations
or /v1/images/edits. Use gpt-image-2, grok-imagine-image, ...
```

每条线路因此多了一个**出图方式**：

| 方式 | 端点 | 适用 |
|---|---|---|
| 生图端点（默认） | `/v1/images/generations` | dall-e-3、gpt-image-2、grok-imagine-* 等纯生图模型 |
| 对话端点 | `/v1/chat/completions` | Gemini / Nano Banana 系列等多模态模型 |

对话端点走 `service.complete()`，再从回复正文里把图片捞出来，依次尝试：
data URI → Markdown 图片链接 → 裸图片链接。`size` 对这类模型无效（Gemini 用 aspectRatio），
需要特定比例就写进提示词。

### 每条线路可单独设超时

GPT 系生图经常跑到 180~240 秒，而**中央模块把生图超时写死封顶在 180 秒**：

```python
# modules/ai_llm/app/service.py  generate_image()
timeout = aiohttp.ClientTimeout(total=min(180, max(30, self._config['request_timeout'])))
```

全局 `request_timeout` 调多大都没用，生图这条路到 180 秒必被掐断，而且 `generate_image()`
没有 timeout 参数、插件传不进去。所以线路上多了一个**超时（秒）**，`0` 表示跟随中央默认：

| 设置 | 走哪条路 | 效果 |
|---|---|---|
| `0` | 中央模块 | 维持原状（实际 ≤180 秒） |
| `10 ~ 180` | 中央模块 + `asyncio.wait_for` | 按设定值提前掐断，适合给慢线路设短限好快点 failover |
| `> 180` + 开了直连调试 | **插件直连生图端点** | 超时真正生效，最长 600 秒 |
| `> 180` + 没开直连 | 中央模块 | 自动按 180 封顶，并在日志里明确告知 |

超过 180 秒必须借道「插件直连调试」——这是中央模块的硬限制，不是插件的选择。
**对话端点的线路也按这个超时掐断**：直连时最长 600 秒，借中央模块时只能比它的全局超时更短。
这个超时**只在重试模式生效**：多图模式下勾了多图的线路不提前掐断（见「多图模式」）。
直连生图的请求体与中央模块完全一致（`model/prompt/size/n`），密钥处理也共用同一套
`_scrub()` 约束：不进日志、不进报错。

> AI 聊天陪伴的生图旁路没有处理超时，它同样直接调 `generate_image()`，
> 所以**所有走中央模块的插件都卡在这条 180 秒线上**。

**不改开关也能自愈**：线路仍设为「生图端点」时，只要中转明确回「该模型不在
`/v1/images/generations` 上」，插件会自动改走对话端点重试一次，不用人工干预。
普通报错（500、429 等）不会触发这个回退，免得白烧一次额度。
面板试跑的故障日志里会标出每条线路**实际用的端点**。

### ⚠️ 插件直连调试（风险功能）

中央模块的 `complete()` 只把 `message.content` 当文本交回来。中转要是把图片放在
**`message.images[]`** 里，插件就拿不到；content 为空时还会先撞上中央模块的
「接口返回了空消息」。`complete()` 也没有透传 `modalities` 的口子。

中央模块是市场模块、改了会被更新覆盖，所以插件提供一个**默认关闭的调试开关**作为过渡。
打开后 `mode=chat` 的线路不再借道 `complete()`，而是由插件**自己**向
`{base_url}/{chat_path}` 发请求（带 `modalities: ["image","text"]`），并按
`message.images[]` → `message.image` → `content[]` 图片分片 → 正文 data URI / 链接
四级兜底取图。

密钥安全约束（都有用例锁死）：

| 约束 | 实现 |
|---|---|
| 关闭时**根本读不到密钥** | `_direct_endpoint()` 第一行就检查开关，不通过直接抛错，之后才碰 `service.config()` |
| 不进任何日志 | 请求头就地构造，从不打印 payload / headers |
| 不进任何报错 | 外抛文本一律过 `_scrub()`，连中转把密钥回显在错误体里也会被抹成 `[密钥已隐藏]` |
| 不落盘 | 每次调用现取现用，插件配置与历史库都不存 |
| 只支持 OpenAI 兼容格式 | `openai_responses`、`gemini` 原生、`novelai` 明确拒绝，不猜请求格式；`gemini_openai`、`grok` 等兼容类型照常可用，Base URL 填成完整的 `…/chat/completions` 也能用（与中央模块拼地址一致） |

代价：这些调用**不进中央模块的调用审计与 Token 统计**，中央面板看不到这部分用量。
所以定位成调试功能——等中央模块支持了 `message.images`，关掉开关即可回到正常链路。

判断该不该开：面板「试跑生图」跑一次，故障日志会原样显示中转的真实回复或报错。

## 对外公开画图能力

画图是**本插件自己的对外工具**：挂在框架的全局钩子（`core.module.hook.get_hook_manager()`）上，
其他插件直接检索、直接调用，**不经过中央 AI LLM**；审核、限额、留档仍然全部发生在本插件里。

> 1.5 ~ 1.7 是把工具注册到中央 AI LLM 共享（`ai_draw:tool:draw` + `call_capability()`）。
> 中央 1.3 起去掉了跨插件共享：它的「插件私有工具」只注入注册者自己的请求，「公用工具」是在子进程里
> 跑的代码（单次最长 120 秒），碰不到本插件的配置、历史库和图床。所以 1.8 起改走框架钩子，
> 也就不再受中央模块版本影响。

| 钩子 | 用法 | 作用 |
|---|---|---|
| `ai_draw.tools` | `pipeline` | **检索**：返回 `tools`（OpenAI function 定义）、`call_hook`、`limits` |
| `ai_draw.call` | `pipeline` | **调用**：按工具名执行，结果放在返回 dict 的 `result` 里 |

```python
from core.module.hook import get_hook_manager

hooks = get_hook_manager()
found = await hooks.pipeline('ai_draw.tools', {})
tools = found.get('tools', [])        # [{'type': 'function', 'function': {'name': 'draw_image', ...}}]

reply = await hooks.pipeline('ai_draw.call', {
    'name': 'draw_image',
    'arguments': {'prompt': '一只橘猫'},   # 模型给的参数原样转交
    'caller': 'my_plugin',                 # 留档标注
})
result = reply.get('result') or {'ok': False, 'error': 'AI 画图没有响应'}
```

检索到的定义可以直接当中央 `complete()` 的**调用级工具**，让自己的模型决定要不要画：

```python
async def tool_handler(name, arguments):
    reply = await hooks.pipeline('ai_draw.call', {
        'name': name, 'arguments': arguments, 'caller': 'my_plugin', 'max_images': 1,
    })
    return reply.get('result') or {'ok': False, 'error': 'AI 画图没有响应'}

result = await service.complete(
    messages, tools=tools, tool_handler=tool_handler, consumer_plugin='my_plugin',
    tool_timeout=300,   # 中央默认 120 秒就掐断工具并终止整次调用，画图常常更久
)
```

没人挂钩子时 `pipeline` 原样返回传入的 dict（没有 `tools` / `result` 键），据此判断本插件没装、
没加载或关了「公开画图工具」；也可以先看 `hooks.has('ai_draw.call')`。

### 参数

模型能填的只有 `arguments` 里的两项；其余由调用方放在外层，模型改不了：

| 位置 | 字段 | 必填 | 说明 |
|---|---|---|---|
| `arguments` | `prompt` | ✅ | 画面描述 |
| `arguments` | `max_images` | | 最多几张，默认 `1` = 单图；`≥2` 且本插件开了多图模式时启用多图，上限是勾了多图的可用线路数 |
| 外层 | `name` | ✅ | 检索到的工具名（`draw_image`） |
| 外层 | `caller` | | 调用方名称，只用于留档标注 |
| 外层 | `max_images` | | 调用方定的张数**上限**：模型要得再多也不超过它（钉死单图就传 `1`） |
| 外层 | `wait_seconds` | | 多图最多等多少秒就返回，默认取面板「多图汇总等待」，范围 10~280 |

不传 `max_images` 就是单图，不会被悄悄改成一次画好几张、多花钱。

`ai_draw.tools` 另外返回 `limits`：`max_images`（当前最多能同时画几张，多图没开时是 1）、
`default_wait_seconds`、`hosting_ready`（图床不可用时对外调用必然失败）。

### 返回值

单图、多图同一个结构，刻意只给链接与元信息：

```json
{"ok": true, "mode": "multi", "count": 2, "pending": 1,
 "images": [
   {"url": "https://图床直链1", "width": 1024, "height": 1024,
    "markdown": "![AI画图 #1024px #1024px](https://图床直链1)",
    "model": "gpt-image-2", "provider": "OpenAI 中转", "record_id": 42},
   {"url": "https://图床直链2", "width": 1024, "height": 1536,
    "markdown": "![AI画图 #1024px #1536px](https://图床直链2)",
    "model": "gemini-3.1-flash-image", "provider": "YTea", "record_id": 43}
 ],
 "markdown_all": "![AI画图 #1024px #1024px](https://图床直链1)\n\n![AI画图 #1024px #1536px](https://图床直链2)",
 "failed": [{"model": "dall-e-3", "provider": "OpenAI 中转", "error": "HTTP 500: ..."}],
 "url": "https://图床直链1", "width": 1024, "height": 1024,
 "markdown": "![AI画图 #1024px #1024px](https://图床直链1)",
 "model": "gpt-image-2", "provider": "OpenAI 中转", "record_id": 42,
 "requested_size": "1024x1024"}
```

| 字段 | 说明 |
|---|---|
| `images` | **永远是数组**，单图时只有一个元素；每项的字段与 1.6 的单图返回相同 |
| `count` / `pending` | 交回了几张 / 交卷时还有几张在画（**这几张不会再补给你**） |
| `markdown_all` | 所有图拼好的一条 Markdown（图之间空一行），直接 `event.reply(md, msg_type=2)` |
| `failed` | 失败的线路与原因；只在多图且确有失败时出现 |
| `mode` | `single` / `multi` |
| 顶层 `url` `width` `height` `markdown` `model` `provider` `record_id` | 镜像 `images[0]`，只认单图的老调用方一行不改 |
| `note` | 要了多张却只画了一张时说明原因（没开多图模式 / 多图线路不足两条 / 今日额度只剩一张） |

`width` / `height` 是**实测像素尺寸**（复用插件自己那套不依赖 Pillow 的头部解析），
不是请求时填的尺寸——请求值另放在 `requested_size` 里，两者对 Gemini 这类模型常常不一致。

`markdown` / `markdown_all` 是拼好的 QQ Markdown 图片语法，调用方直接发即可，
不用自己再去量宽高。单图返回体约 600 字节（`images` 与顶层各一份）。

### 多图对外调用的时间线

- 从本插件**开始审核**算起，到 `wait_seconds` 为止画好的**全部**放进 `images` 一次交给你；
  全部提前画完就提前返回
- 交卷以后没画完的接着画到 290 秒，画好**只留档**（`delivered=0`），不传图床、不补给你 ——
  你早就拿着结果走了
- 到点一张都没画好：`ok=false`，`error` 写明还有几张在画，`pending` 给出张数
- 多图线路全部失败时，同样按顺序试一遍没勾多图的线路兜底（同样受 `wait_seconds` 约束）

`wait_seconds` 的计时比调用方自己的计时**晚开始**（不含调用方排队、模型思考的时间），
所以要比调用方的超时**短 10 秒以上**，否则调用方先超时，一张也拿不到。

### 调用方超时离开

每次调用都跑在独立的会话任务里。调用方自己 `wait_for` 超时取消时，本插件**照常画完并留档**
（记「调用方已超时离开，图片只留档」），不会把已经在画的图扔掉；但不再换线路重试、
也不再占图床额度 —— 没人收了。插件卸载时还在跑的会话会被收掉，已出的图照样留档。

### 调用方怎么接

从 1.7 的 `call_capability()` 迁过来只改「怎么找到、怎么调」，参数和返回体不变：

```python
# 1. 调用：经框架钩子；wait_seconds 比自己的超时短 10 秒以上
timeout = float(current.get('draw_timeout_seconds') or 120)
hooks = get_hook_manager()
if not hooks.has('ai_draw.call'):
    return {'ok': False, 'error': 'AI 画图没装、没加载或没开「公开画图工具」'}
reply = await asyncio.wait_for(hooks.pipeline('ai_draw.call', {
    'name': 'draw_image', 'arguments': {'prompt': prompt}, 'caller': CALLER,
    'max_images': 3, 'wait_seconds': max(10, int(timeout) - 15),
}), timeout)
result = reply.get('result') or {'ok': False, 'error': 'AI 画图没有响应'}

# 2. 读结果：images 永远是数组
images = result.get('images') or ([result] if result.get('url') else [])
for item in images:
    url = item['url']
    width, height = item.get('width') or 1024, item.get('height') or 1024

# 3. 发送：多张拼成一条 Markdown，别一张占一次被动回复（群聊可在开头加 <@openid> 换行）
text = result.get('markdown_all') or '\n\n'.join(
    f'![画图结果 #{i.get("width") or 1024}px #{i.get("height") or 1024}px]({i["url"]})'
    for i in images
)
await event.reply(text, msg_type=2, skip_suffix=True, force_verify_image_resource=True)
```

注意 `pending > 0` 时没画完的那几张**不会**再给你，别等它们；也别为了「凑满张数」立刻重调 ——
那几张还在画、还在计费。缓存（如 LGTBot游戏问答 的 `draw_cache`）要存整组链接而不是只存第一张。

### `url` 一定是本机图床直链

**绝不返回 AI 接口的原始链接。** 那个域名没在 QQ 开放平台报备，调用方拿去发 Markdown
图片会被拦下、图不显示。所以对外调用固定走「拿到字节 → 上传图床 → 返回图床直链」，
任一步失败就返回 `ok=false`，不拿接口链接糊弄过去：

**每条线路都要走完「出图 → 拿到字节 → 传图床」，中间掉链子就换下一条线路重来**——
与聊天指令同一套故障转移，次数同样受「投递失败换线路重试次数」控制：

| 情况 | 结果 |
|---|---|
| 接口只给了服务器下载不到的链接 | **换下一条线路重新出图** |
| 图床活着但收不下这张图（格式 / 体积） | **换下一条线路重新出图** |
| 压根没有可用图床 | 一调用就 `ok=false`，**一张都不画** —— 画了也交不出图床直链 |
| 线路全试完仍不行 | `ok=false`，逐条列出每条线路的原因 |
| 任一条成功 | `url` 与 `markdown` 都指向图床，历史里记下先前失败的线路 |

多图调用时每条多图线路只画一张：某条取不到字节或传不上图床就只算它失败，
不在这条线路上重试，结果里也不会出现它（兜底规则见上文「多图对外调用的时间线」）。

接口原始链接只留在历史库的 `image_url` 里供排查，**不出现在返回值的任何字段**。
面板「对外能力」在没有可用图床时会直接标黄警告，不用等调用失败才发现。

生图成功但转图床失败时，记录仍记 `status=success` + `delivered=0`（与聊天链路
「生成成功但未送达」同一套语义）——钱确实花掉了，每日配额如实计数，
避免调用方无限重试却不占额度。

> ⚠️ **绝不返回 base64**。工具结果会回灌进调用方模型的上下文，一张 1MB 的图
> 转成 base64 约等于几十万 token，一次就能把上下文撑爆。

极少数格式量不出像素尺寸时，`width` / `height` / `markdown` **三个键直接不返回**，
而不是给 0 —— 免得调用方拿 0 去拼出坏掉的 Markdown。

调用方约束：

| 项 | 说明 |
|---|---|
| 违规词 / AI 内容审核 | 与聊天指令同一套，先审再画 |
| 每日上限 | 面板「对外能力」单独设（默认 50 张，按出图张数算），与全局每日额度叠加；剩余不够就少画几张 |
| 并发 | 与聊天指令共用同一个并发闸；一次多图调用只占一个名额 |
| 留档 | 记录 `source=capability`，运行日志里能单独筛出来 |
| 失败 | 一律返回 `ok=false` + 原因，绝不把异常栈抛进模型 |

钩子调用**拿不到 Event**，所以做不了按用户的冷却与配额——`caller` 是调用方自报的，
只用于留档标注，不做鉴权。真正的成本闸是上面那个每日上限。

钩子是进程内全局的：开着「公开画图工具」时，**同一机器人进程里的任何插件**都能检索与调用
（不再有中央面板的授权名单）；关掉开关即摘下。插件加载时挂上、卸载或热重载时按 owner
（`AI画图`）摘下，热重载不会留下两份回调。

## 处理流程

1. 场景开关、描述长度上限与本地违规词
2. 频率检查：每人冷却、每会话冷却、每人每日、全局每日。
   **被限流的请求只回一句提示，不写运行日志** —— 它没有真正发起画图
3. AI 内容审核：独立一次模型请求，只接受「安全」或「内容违规，已禁止发送」
4. 提示词优化：中央对话模型把中文描述改写成生图提示词，失败回落原文
5. 拼接固定前后缀并截断
6. 按线路顺序出图：生图端点走 `generate_image()`，对话端点走 `complete()`，失败自动切下一条；
   配了两条以上多图线路时改为**同时开画**（见「多图模式」）
7. 上传图床 → 发 Markdown → 写入历史；**生成成功却没送达时换下一条线路重来**

并发闸只套在第 6 步的生图上（多图一次请求只占一个名额）；审核与提示词优化不占额度。
第 3 步起整个流程受 290 秒总时限约束。

### 试跑生图

只在面板里预览，**不上传图床、不发到聊天**——省掉一次图床额度。
图片优先读本地留存（`/image?id=N`）；关掉「保存图片到本地」时改为内联 data URI 返回，
预览不依赖任何存储设置。这类记录在运行日志里标为「面板试跑」，与真实投递区分。

试跑**逐条线路单独跑**（不让中央模块把失败合并成一句话；也不走多图并发），页面上给出完整的故障转移日志：

```
#1 失败   OpenAI 中转 / dall-e-3   1.2 s   HTTP 500: upstream provider exploded, request-id=abc123
#2 成功   备用中转 / sd3           8.4 s   成功
```

每条线路的**原始报错原样保留**（不截断成 500 字），带耗时和顺序，全部线路失败时也一样列出。
这些日志只回给页面、**不入库**，历史里仍旧只留一条汇总记录。

某条线路只给了服务器下载不到的 URL 时，试跑仍会用它出预览，但标注
「聊天里这条线路会被判定失败」—— 免得面板看着正常、群里却发不出去。

## 限流

框架 `@handler(cooldown=...)` 只是存进 handler 字典、`core/` 里没人读它，所以自己实现：

| 项 | 默认 | 取值 |
|---|---|---|
| 画面描述最大字数 | 1000 | 10 ~ 4000 |
| 每人冷却 | 30 秒 | 0 = 关闭 |
| 每会话冷却 | 5 秒 | 0 = 关闭 |
| 每人每日 | 20 张 | 0 = 不限 |
| 全局每日 | 200 张 | 0 = 不限 |
| 最大并发 | 2 | 最小 1 |

超长与被限流的请求一样，只回一句提示、**不写运行日志**，也不吃每日额度。
超长文案支持 `{limit}` 占位符。

每日配额按**成功出图的张数**算（多图一次算几张），失败与拦截不吃额度。冷却在内存里，
每日配额从 SQLite 现算，热重载不会清零。

## 数据

`data/`（已 gitignore）：

- `config.json` —— 插件配置，不含 API Key
- `history.db` —— SQLite 历史记录，默认留 500 条；多图每张一条，同一次请求共用 `batch_id`
- `images/` —— 本地留存的出图，默认留 200 张，滚动清理

接口返回 URL 时，留存前会校验目标是公网地址，拒绝回环、内网、链路本地与云元数据地址。
历史与图片超上限时，旧记录连同图片文件一起删除。
